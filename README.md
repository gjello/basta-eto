# Oliver Family Exchange Gift

The public page shows only whether each wishlist has been completed. A member must enter that name's 4-digit PIN to read or change its wishlist. The server verifies PINs and serves only the signed-in member's wishlist, and after everyone is ready, that member's assigned recipient and wishlist. PINs are salted and hashed on the server.

There is no email or Google sign-in screen. The first person to choose an unclaimed name and set a PIN claims that name. Since there are no invite codes, share the site only with the intended group and ask members to set PINs only for their own names. Use a PIN that is not used for banking or other accounts. Photos and names included in the public site are visible to anyone who can open its URL.

## Important: keep direct Firestore access blocked

The website's Netlify function is the only intended data access path. In Firebase Console, open **Firestore Database > Rules**, replace the rules with the contents of `firestore.rules`, and click **Publish**. These rules deny all browser access; the Netlify server accesses Firestore using its private service account. Do not use the old rules that allowed anonymous or public reads.

Existing records in the `wishlists` collection are migrated for each name when that member enters their existing PIN. Existing PIN hashes were generated by the old site and are upgraded to salted hashes on successful login. Firestore rules do not block this server-side migration.

## Set up the Netlify server function

### 1. Create a Firebase service account key

1. Open https://console.firebase.google.com/ and select the `christmas-exchange-cecbb` project.
2. Open **Project settings** (gear icon) > **Service accounts**.
3. Open **Google Cloud Console** from that page.
4. In Google Cloud Console, open **IAM & Admin > Service Accounts** and create a service account, for example `netlify-exchange`.
5. Grant it the **Cloud Datastore User** role. Do not grant Owner or Editor.
6. Open the service account, choose **Keys > Add key > Create new key > JSON**, and download the key. Keep it private; never put it in this folder, GitHub, or the website.

### 2. Create a session secret

On Windows, open PowerShell and run:

```powershell
$bytes = New-Object byte[] 48
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($bytes)
[Convert]::ToBase64String($bytes)
```

Copy the printed value. Keep it private.

### 3. Add both secrets to Netlify

1. Open your Netlify site and go to **Project configuration > Environment variables** (sometimes **Site configuration > Environment variables**).
2. Add `FIREBASE_SERVICE_ACCOUNT`. Its value is the complete JSON text from the downloaded service account key file.
3. Add `SESSION_SECRET`. Its value is the random string generated above.
4. Save both values. Never add either secret to `index.html` or commit either one to a repository.

## Deploy the folder with its server function

The Netlify function must be deployed along with the site; a static-only drag-and-drop deploy is not enough.

1. Put this entire folder in a **private** GitHub repository, including `index.html`, all the photos, `package.json`, `netlify.toml`, `firestore.rules`, and `netlify/functions/api.mjs`. Do not upload the service-account JSON file.
2. In Netlify, choose **Add new project > Import an existing project**, connect GitHub, and select that repository.
3. Leave the build command empty. `netlify.toml` configures the publish folder and server function.
4. Deploy the site and wait for the deployment to finish.
5. In Netlify environment variables, make sure both secrets are available for the deploy context you used, then trigger a new deploy so the function receives them.
6. Open the Netlify URL. The status should say **Connected — wishlist status syncs across devices**.

Test with a non-sensitive wishlist: enter a name, set a PIN, save a wishlist, and open the public status page in another browser. That browser should see only completion status. The wishlist itself should require the name's PIN.

## Reset a name's PIN

If the wrong person claims a name, an owner can reset it in **Firestore Database > Data**:

1. Delete that name's document in the `members` collection.
2. Delete the same name's old document in the `wishlists` collection, if it exists. Document IDs use URL encoding; for example, `Tita Cheche` is `Tita%20Cheche`.
3. Delete `public/status`. It is rebuilt from the remaining member records the next time the site loads.

This resets the PIN but also deletes that member's saved wishlist, so they will need to enter it again. Deleting documents in the Firebase console does not require opening up the Firestore rules.
